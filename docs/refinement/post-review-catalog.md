## Implemented consumers and explicit surface differences

- Shared source portion semantics live in `shared/mobile-domain/catalog-measures.ts` and `src/lib/services/catalog-food-context-service.ts`. Web `catalog-food-context.tsx` and native `scanner-screen.tsx` consume the same full portion label and supported gram amount.
- Web `food-catalog-picker.tsx` applies a source portion to the Pantry draft and passes the reviewed measure to `recipe-form.tsx` / `import-review-form.tsx`. `nutrition-recording.tsx` exposes measures only for a saved nutrient record whose frozen source snapshot matches and whose supported unit includes grams; selection does not log food.
- Native scanner destinations remain Pantry or the local shopping cart. Native `nutrition-source-portions.tsx` now supplies the separate eaten-amount workflow: it reads measures for the saved record’s exact catalog reference and copies a whole source gram weight only when server-provided `supportedUnits` includes `g`. Other portions remain informational. The entered amount/unit is unchanged until explicit selection; manual editing remains available and no density is inferred.
- Web `catalog-retail-evidence.tsx` has the manual identified-product enrichment action. The native assistant can invoke the same curated read operation; the scanner does not contain a dedicated manual enrichment control. No free-text matching or external retailer basket is implied.
- Native local store/route editing remains available. Official chain/area/proximity/pagination and branch linking use the explicit same-instance `/settings/lists` handoff. The destination exists and is covered by web contracts; opening/authenticating it through an actual native OS is still blocked by device availability.
- Native assistant proposal details use `shared/mobile-domain/proposal-review.ts`. Supported top-level scalar fields prepare a new version-bound review; nested/structured changes use a deliberately prepared conversation draft. Neither path automatically applies or sends. Raw identifiers and expected versions are not offered as ordinary editable fields.

The [capability matrix](capability-matrix.md) records these supported paths and handoffs. The [inventory](inventory.json) separates route files, methods, source modules, direct tools and dispatched operations; its counts establish source presence only.

## Restart and identity contract

`GET /api/v1/auth/context` is a session-only, private/no-store response containing only `{actor:{userId,profileId}}`. It does not require Nutrition access or expose profile preferences. Before native scanner confirmation/retry, this actor must equal the original journal actor. The reviewed Pantry batch/catalog-import and shopping catalog-item POST routes also validate optional `X-Bord-Expected-Profile-Id`, returning 400 for malformed IDs and 409 for a changed actor before domain writes. Authentication, origin and normal operation permission checks remain required.

The scanner journal commits encrypted chunks before its manifest, reads them back before HTTP, and refuses to replace unresolved work. It contains only the necessary reviewed operation and human destination summary. A process restart reloads that command; it never silently scans/creates/retries. A successful server response is independent of workspace refresh. A local cleanup failure retains the command for receipt reconciliation.

Assistant journaling stores only instance/account/profile/thread/operation identifiers and preparation time. Private message text and attachments remain in-memory drafts and are cleared on logout; they are not restored after a process kill. The reference remains encrypted and is discoverable only after signing into the same account/instance. Original-profile mismatch blocks retry/review. An exact server lookup distinguishes running/completed/failed/cancelled/outcome-unknown; time alone is never success. Explicit acknowledgement of an absent receipt creates a server tombstone, so a delayed original request cannot execute after the person chooses to continue. Reconnection never automatically resends writes or paid work.

Scanner commands retain their original operation after unknown outcomes and after rejected uncertain retries. Signing out does not delete the unresolved encrypted operation: deleting it would lose the ability to reconcile a possible committed write. Other account/instance keys cannot read or submit it. This retention is separate from ordinary draft clearing and excludes credentials/images. There is no automatic expiry that converts uncertainty to “not applied.”

## Final native Nutrition portion follow-up

The missing native source-portion picker was completed after the initial inventory, using an additive application contract rather than reconstructing a current provider reference. Existing `GET /api/v1/nutrition/products/{productId}/records` retains `records` and adds `preferredRecord`; both projections include frozen `catalogRef` and server-calculated `supportedUnits`. Preferred selection uses the existing source-priority rules. Corrections select their original `foodNutritionRecordId` from history and never substitute the current preferred record.

Native product logging pins `expectedFoodNutritionRecordId`. The product-intake service checks that ID against the applicable original/preferred record inside the write transaction; a changed record returns 409 without logging. The web consumer also pins its reviewed record. Existing callers may omit the additive field; this does not make an unpinned historical request a reviewed-record guarantee. API authorization and trusted-origin checks remain unchanged.

The picker is scoped to account/instance, product, saved record/revision, catalog source/revision/generation and basis. Old request completions cannot replace the current source. Loading or failed lookup never writes an amount. Selecting a valid portion copies its full gram weight, with no division by the stated cups/servings and no inferred density. Missing/zero weights or an unsupported gram conversion remain informational. A source change retains the entered amount but requires a new portion choice or deliberate manual review. Confirmation locks fields and source selection; an unknown result sends the person to diary review rather than offering an automatic resend. An acknowledged save followed by failed dashboard refresh remains labelled saved. These in-form safeguards are separate from the scanner’s durable restart journal.
