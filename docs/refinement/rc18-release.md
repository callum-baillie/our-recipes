The Docker build context now excludes nested native dependencies, local native build output, screenshots and nested environment/credential files. The shipped standalone denylist/runtime checks remain in place. Service-worker tests derive their current version from package metadata while retaining assertions against the actual worker.

The new local runtime check reproduced a container-only restore failure: staging beside `/data` required writable parent storage, and renaming a mounted data root would also be invalid. Restoration now stages/replaces owned files within the existing mount, preserves archive storage, rolls back failed file installation or integrity checks, and retains recovery files if rollback fails. Regression cases cover an unwritable parent, unchanged root identity, partial-install rollback, SQLite sidecars, incomplete rollback and competing restores. Actual disposable-container verification remains a separate required check.

A durable restore marker blocks database use after interrupted/incomplete recovery instead of initializing a new database; health reports `503 recovery_required`. Successful verification or complete rollback removes the marker. A clean-runner accessibility check also caught a missing document title during cooking-route refresh despite an earlier title assertion. Household metadata now uses Next's documented blocking-metadata option, and the browser fixture checks a populated title in the document head without disabling axe rules.

The actual container then exposed the auth adapter's captured closed SQLite handle after restore. Its Drizzle root methods now resolve the current database at operation time while preserving concrete transaction objects. A real-library synthetic-session regression checks old-session revocation and fresh sign-in through the existing auth instance after restore; the container smoke exercises that same lifecycle over HTTP.

## Upgrade and rollback

Create, download and validate a backup of the current installation before upgrading. Keep it outside the application volume and record the prior image digest. Pull the versioned image, retain the existing dedicated `/data` mount and configured secrets/origin, then require health to report version `1.0.0-rc.18`, schema `0071_ai_prompt_versions` and `migrationStatus: current` before accepting writes. The existing entrypoint takes a pre-migration SQLite safety copy. Do not point an older image at the migrated database; use a fresh data directory and the prior version's supported restore flow with the pre-upgrade backup. See [deployment](../deployment.md) and [backup recovery](../backup-and-restore.md).
