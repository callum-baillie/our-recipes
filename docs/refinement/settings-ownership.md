## Nutrition authentication and viewed-person contract

First-party Nutrition routes authenticate the Better Auth session from the request. A signed `bord_active_profile` cookie selects a viewed subject; it is not a substitute for an account session and never supplies the authorization actor. The compatibility Nutrition principal and household actor resolve from the signed-in account's linked profile. A Child account stays a Child when viewing an adult. A Parent/Admin viewing a Child retains only the account's existing explicit guardian permissions; changing the viewed profile creates no grant.

`GET /api/v1/nutrition/session` returns:

```json
{
  "actor": {
    "householdProfileId": "signed-in-account-linked-household-id",
    "nutritionProfileId": "signed-in-account-linked-nutrition-id",
    "viewedHouseholdProfileId": "selected-household-subject-id",
    "viewedNutritionProfileId": "selected-nutrition-subject-id"
  }
}
```

The IDs are distinct concepts even where existing converged data uses identical values. Consumers must not treat viewed IDs as authority. Missing/revoked sessions return `401 authentication_required`; permission failures return `403` through the existing role/domain errors. All target-profile operations still validate their grants at the service boundary. API keys do not establish this browser/native session. The retired separate Nutrition-session POST/DELETE remain410 and direct people to the global profile workflow.

A test-only, no-auth-configured seam remains for existing isolated domain fixtures. Configured installations always require the authenticated account. Direct real-session integration fixtures exercise signed-cookie-only, Child/adult, Parent/admin, guardian/Child and revoked-session cases, including the real proxy policy.

`GET /api/v1/ai/summaries` is also a private signed-in-account result: it requires the account's own active profile. `POST` refresh always targets the linked account and returns its named recipient. It cannot refresh another person's summaries because the global viewing profile changed. The first-party routes remain listed in `docs/openapi-internal-routes.json`; this contract documents their supported web/native semantics without adding a duplicate external integration endpoint.
