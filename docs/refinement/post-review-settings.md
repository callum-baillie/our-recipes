## Shared reconciliation contract

`mergeSettings(baseline, draft, current)` compares leaf values against the acknowledged baseline. It adopts current values where the draft did not change, retains independent local edits, and returns every overlap with baseline/local/current values. A matching change on both sides is already agreed. Arrays are atomic selections; workload/account collections are projected to keyed records first. Removed overrides remain absent. Version fields are excluded from editable comparisons and reconstructed exclusively from the current response.

`SettingsMergeReview` presents native radio choices with visible labels and comfortable targets. It does not silently pick a local value, save, preview an estimate or invoke AI. All overlaps must be resolved before accepting the reviewed draft. Discard deliberately adopts the loaded saved snapshot. Form fields are locked during review so displayed choices cannot drift. A later server conflict leaves the reviewed draft intact and restarts current-value review.

The same shared review is also used by the adaptive interview workstream. Its independently versioned answer contract remains separate from My profile.

## Internal API compatibility

- `GET /api/v1/account/profile` returns `{profile, revision}` for the linked account, private/no-store. `PATCH` now requires `{expectedRevision, settings}`; `settings` is strict and excludes `goalContext.kitchenInterview`. Missing/stale revision returns400/409 rather than accepting an old full-profile snapshot. The only active first-party caller is updated. This internal route is listed in `docs/openapi-internal-routes.json`, not advertised as a new external integration contract.
- `GET /api/v1/nutrition/profiles/:id?scope=settings` returns the current private preference snapshot under the same `manage_profile` permission already used by the account editor. The default GET retains its existing shared-summary behavior. Both use the authenticated account actor; selecting a viewed household person does not grant access. `PATCH` keeps `expectedVersion` and existing validation.
- No migration, changed authentication mechanism, provider activation or new external service is required.
