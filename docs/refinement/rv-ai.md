## Durable history and compatibility

Migration `0075_ai_chat_privacy_scope` adds one nullable `ai_chat_threads.privacy_scope_json` column. It contains identifiers, role capabilities and boolean policy metadata; no names, messages, tool results, nutrition values or credentials. Thread-list responses omit it. A legacy nonempty thread has no verifiable historical scope and requires a new conversation before further model work. Reading saved history is preserved. Newly scheduled conversations seed the metadata from the current authorized linked owner before any evidence or proposal exists. The worker revalidates that scope and passes the same principal into generation; normal post-generation chat continuation is permitted, while later contraction remains blocked. This is deliberately conservative because removing arbitrary private facts from generated free-form history cannot be made reliable by string replacement.

The focused upgrade fixture removes only this new column and migration marker from a synthetic existing database, reapplies migration, and checks preserved messages, null legacy baseline, foreign keys and blocked retransmission. Existing pre-0068 upgrade coverage was updated to remove the new column when constructing that historical schema.

Migration number 0074 belongs to concurrent, unpublished My Kitchen work in the primary checkout and is deliberately absent here. **Integrate and order both unpublished migrations before deploying either combined result.** Deploying 0075 first and later adding an older timestamped 0074 would cause the timestamp-based migrator to skip 0074. No primary-checkout migration has been modified.

There is no `allowPersonalInstructions` policy in the current architecture. Personal instructions remain a permitted account preference; their approved text is frozen, while global/account/workload enablement, model/reasoning/image override policy and stricter limits remain authoritative. No new policy switch was invented.

## Independent review follow-ups

The independent review found a legitimate-flow regression: a scheduler-created thread could acquire a proposal without a privacy baseline and subsequently be refused as legacy history. The fix seeds the metadata before adding evidence and proves continuation through an actual serialized chat request. Legacy nonempty threads still cannot acquire a retrospective baseline.

The review also found that a completed input-file upload was followed by `batches.create` without renewing the authorization checks. The real Batch client now invokes a synchronous check after preparing the upload and again after upload, immediately before paid submission. The callback rechecks account access, current sharing for the saved evidence, lease ownership, original item/configuration identity and current constraints. It regenerates the bounded JSONL and compares it with the prepared file; stricter caps or changed permissible options cannot silently submit stale uploaded bytes.

A failure before entering `batches.create` records `provider_submission_not_started`, settles affected candidates as failed and attempts deletion of the known uploaded file. Revocation cannot retract bytes legitimately uploaded earlier; cleanup is not described as guaranteed provider erasure. Once the paid request is entered, transport uncertainty retains the existing unknown-outcome classification and reconciliation guard. Tests cover sharing, reasoning, timeout, output-cap, account and workload contraction; cancellation; unchanged approval; image candidate failure; and a lost paid-submission response. No live provider call was made.

One follow-up fixture initially supplied a personal override version to the shared-workload save and correctly received a conflict. Its unresolved fake upload caused dependent test failures. The fixture now uses the shared version and always releases/joins the paused worker; all 11 cases pass.

## Limits

These tests establish application-side serialization, permission gates, stored approval selection and migration behavior. They do not establish provider execution, cost, live scheduling latency, visual quality or browser/native presentation. Broader release gates and the independent bypass review are coordinated by the lead agent. Recovery remains explicit; no uncertain operation is automatically resubmitted.
