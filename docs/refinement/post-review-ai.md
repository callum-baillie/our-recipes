## Final acceptance cross-check

### F14/G08 reading during viewport changes — targeted fix verified; production rerun pending

The later production browser run passed 20 scenarios and failed its chat Jump-to-latest check. That fixture changed `scrollTop` and dispatched a scroll immediately after resize, while the drawer deliberately ignored layout-driven scroll events for two animation frames. Inspection identified a real adjacent race: deliberate wheel, touch, keyboard or scrollbar reading in the same interval could also be ignored, allowing a queued viewport callback or streamed fragment to restore the bottom.

The drawer now records deliberate scrolling intent before native movement. Viewport adjustments retain that intent, new fragments preserve the reading position and expose Jump to latest, and an actual return to the bottom or Jump restores following. Downward gestures at an already-bottom conversation and clicks inside message content do not pause following. The production fixture now uses real wheel and Home input, asserts the reading position after a fragment, then checks that Jump exposes the latest text; it no longer treats a synthetic scroll event as evidence of user input.

## Compatibility and recovery

- Additive migration `0072_ai_execution_recovery.sql` introduces leases, owned draft provenance, turn linkage and execution traces. Existing completed chat receipts continue to replay. An old running receipt without a lease is conservatively marked unknown after its legacy grace period.
- The confirm-only recipe image API is intentionally no longer a write path. Use the documented preview operation then explicit candidate acceptance. Legacy draft previews without account/digest provenance cannot be silently promoted; legacy queued images without source revision require fresh review.
- `GET /ai/chat/threads/{id}?operationId=…` returns the exact owned receipt. `PATCH` with `action: acknowledge_recovery` records deliberate review. It never replays work. New operations remain blocked by an active or unreviewed unknown turn.
- An uncertain OpenAI Batch submission records `provider_submission_outcome_unknown`. Automated retry is refused because acceptance at the provider is unknown; an operator must reconcile it before deliberately authorizing another paid job. SDK retries are disabled.
- A cancelled request can still have consumed provider resources. Late output cannot attach an image, overwrite a closed draft or turn an unknown receipt into success. Accepted earlier writes and independent queued work remain discoverable.
- No fallback model is silently chosen. Unknown custom model capabilities are not fabricated; providers may reject unsupported custom configurations. Decisions has a fixed supported contract and is recorded independently of Responses token controls.
