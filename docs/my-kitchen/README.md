## Ownership and architecture

`/my-kitchen` is a household workspace linked from Settings and My profile. The administrative Settings layout is unchanged. Parents/admins retain shared CRUD, children can read, and the service independently rechecks the current authenticated account, its linked profile and effective active-profile role. Profile switching cannot elevate an account. Browser/native commands carry the reviewed profile header; durable command receipts bind user, active profile, kitchen and normalized intent. Personal cooking preferences always use the authenticated account’s linked profile, even when another household profile is active.

Migration `0074_my_kitchen` adds kitchens, physical equipment, immutable operation receipts/audit snapshots, resource claims, recipe requirements and a default-off AI equipment-sharing category. One stable primary kitchen is created per household. Names, types, models and capacities have no uniqueness rule; identical physical items retain separate UUIDs. Archived records remain addressable. Existing SQLite backup behavior includes these tables, but no new production backup/restore acceptance is claimed here.

The browser imports domain schemas/catalogs, never SQLite, files or credentials. Inventory API handlers, native requests and curated assistant actions call `kitchen-inventory-service.ts`. No provider connection is needed for inventory or deterministic checks. The signed recipe `ActorContext` seam remains unchanged; equipment mutation audit snapshots store the authenticated account and effective profile explicitly.

`kitchen-feasibility.ts` is a bounded deterministic greedy allocator over up to 40 phases, with up to 20 physical units per requirement. It uses actual instance/zone/vessel/accessory/shared-resource IDs, capacity basis/unit compatibility, induction compatibility, availability, dependencies and hands-on limits. It can check multiple recipes together. Sequence mode uses relative order, including supplied release/holding/transfer/cleaning occupancy. It does not infer overlap from a calendar date/meal slot. Failure means unresolved constraints, not mathematical impossibility.

One multicooker’s modes share one base. Spare inner pots/lids never create heating bases. Independent zones require an explicit confirmation and a supported facility/air-fryer type. Racks are not independent cavities. Oven co-use requires matching confirmed mode and temperature, known usable cavity dimensions and measured dish footprints including clearance. The bounded fit check uses same-level strips; it assumes no stacking, rotation or extra capacity from shelves. Missing footprints keep cavity use exclusive, and unknown dimensions remain needs-information. Capacity is never inferred from servings, ingredient density or pan diameter. Batch quantity/time optimization is not implemented.

Previews do not claim resources. Starting a tracked phase revalidates source revisions and claims its entire bundle in an immediate SQLite transaction. A conflicting bundle claims nothing. Future phases are not locked. Resources stay in use until physical release is acknowledged, including after timers, browser disconnection or chat cancellation. A durable physical-use receipt binds each bundle. Exact start replay reconciles an active or released use; it never restarts a released use. Release requires the use token shown by the review, so an old retry cannot free a later use. The starting account can acknowledge release; an administrator can explicitly recover another owner’s abandoned phase only after physical review and a live account/effective-profile authority check. My Kitchen provides this review surface. Manual cooking remains available and is not described as conflict-verified.

Recipe requirements are generic, portable capability/quantity/measurement/step references, never household equipment IDs. Unrelated edits preserve them. Instruction edits invalidate carried-forward unchanged requirements instead of silently rebinding their indices. Planned overrides now preserve method, equipment, requirements and prep/cook/rest timing in the common effective recipe projection used by API/cooking/native/print paths. Legacy overrides omit those optional fields and inherit the pinned recipe baseline. Method-only changes preserve ingredient-based nutrition values; ingredient/yield changes invalidate them. No images are generated by this path.

## Everyday use

Open **My Kitchen** from Settings or My profile. Add equipment by generic type; nickname, make/model and size are optional. Count creates separate physical records. **Add another like this** copies an item into a new draft; editing/removing selects one existing instance. Removal is archival. **Unavailable until restored** means persistent availability, not “busy tonight.” Equipment marked physically in use must be released before edits.

A brand name is not a specification. Choose a pressure/air-fry variant only when confirmed. Enter independent burners/cavities/baskets only when they can really operate separately; shared restrictions can serialize zones. Shelves and extra pots do not count. Espresso brewing, coffee grinding, water heating, milk steaming and milk frothing are different capabilities. The generic espresso templates do not assume grinders or steam wands.

**How I cook** links to account-owned preferences. These do not edit dietary restrictions, allergies, Nutrition consent, household equipment or another person’s defaults. A contextual preference such as “Prefer stovetop potatoes” is a soft preference, not a universal method ban. The existing free-text interview remains personal and is not imported into shared inventory.

Equipment sharing is separately controlled in **My profile → AI preferences & privacy → Equipment and facilities**. New and migrated accounts default off. Without consent, provider context is `withheld`, not an empty kitchen. With consent, compact context includes actual resources/revisions, capabilities, measurements and availability; personal cooking preferences also require recipe-preference sharing. Queued snapshots recheck consent and material kitchen revision before use. No personal interview text is published as equipment metadata.

The assistant can prepare additions, corrections, availability and archival through the existing action-card workflow. For “I just got a new Instant Pot,” a generic electric pressure cooker leaves size/model unknown and does not imply air frying. Clarification updates the acknowledged acquisition ID; “another” is a separate deliberate addition. The deterministic operation test covers reviewed execution/replay/clarification, not live language-model interpretation.

The native **Settings → My Kitchen** screen uses the same API for list/add/edit/duplicate/archive/availability. It preserves existing fields in edits and labels drafts unsaved. It does not automatically replay offline mutations. Restart recovery retains unsaved account/profile/kitchen/instance-scoped drafts in the existing native cache. Reviewed writes use an encrypted write-ahead command journal; restart offers explicit reconciliation of the same operation ID rather than replaying automatically. Core measurements, compatible attachments, material/induction/oven/lid facts, independent compartments and optional guided setup are available. Native device behavior remains unverified.

## Catalog extension

`src/lib/domain/kitchen-catalog.ts` owns versioned local generic templates, categories, aliases, capabilities, relevant measurement family and resource kind. Add a stable key; preserve old keys and increment `KITCHEN_CATALOG_VERSION` when changing the catalog. Aliases are search terms, not model verification. Defaults must be conservative generic type facts. Do not attach manufacturer limits to an entire brand. Template changes affect new drafts, not existing owned equipment. Specific manufacturer-reference provenance and model lookup are not implemented; no live manufacturer lookup is performed.

## Cooking snapshots, dated restrictions and accepted plans

New cooking sessions capture their effective recipe at start, including an already adapted or pinned planned meal. Reopen the `?sessionId=…` cooking URL to resume that snapshot. **Adapt this session** offers explicit method, equipment, instructions and timing review; it saves only to this owned cooking session. The library and other meals keep their own content. The same operation is available to the assistant's existing reviewed-action workflow. No automatic image generation is started.

Session changes use an independent increasing revision, account and active-profile ownership, an expected kitchen revision and a durable operation ID. Undo is a new compensating revision of the latest acknowledged change. A stale or occupied session rejects the change and retains the open form. Explicit ingredient/yield changes clear carried nutrition values and flag ingredient review; Pantry derives the review from the session snapshot, with new or ambiguous ingredients left unmapped. Method-only changes preserve ingredient IDs and evidence. Existing sessions without snapshots remain compatible with historical cooking and cannot be silently claimed as new account-owned adaptations.

**This cooking episode** can exclude recorded items on one explicit local date in an IANA timezone. This is a task restriction, not shared unavailability or a saved preference. The date and active/inactive state remain visible on reopening. Restrictions do not affect other episodes or release equipment already physically in use. For equipment that remains broken until restored, use My Kitchen availability instead.

**Accept equipment plan** persists the reviewed request and allocation without taking any physical claims. Phase start rechecks the effective recipe, kitchen and episode revisions, dated restrictions and exact saved allocation. A stale plan remains available for review with `needs-review` state. Future assignments and physical-use claims stay separate. Finishing a timer, chat cancellation and disconnect do not release claims; the existing acknowledged release controls still apply.

The current manual session editor supports method changes to existing steps. Automatic method selection, richer step insertion/batching, dedicated native session-adaptation screens and the remaining K-register gaps are unfinished.

## Guided setup and measurement editing

`/my-kitchen/setup` offers optional shared inventory setup, Back, skip/resume, separately owned personal preferences and a final saved-facts review. Common appliance shortcuts ask whether the item is a separate device or another function of recorded equipment. Adding a function updates the selected physical base through the normal reviewed editor; it does not add a second base. Equipment drafts and step progress retain their original scope and versions. Sharing remains unchanged until its explicit save, even when the user finishes or skips setup. The native screen offers the same optional progression, using its regular inventory editor and canonical preference/sharing APIs.

Multiple measurements can be recorded on one item. Preserve the entered value and unit: choosing another unit relabels the value, rather than converting it. A measurement describes nominal volume, a working limit, dry input, cooked output, mass, slices or a specific dimension. Device rice cups need their own mL volume. Unknown values are omitted, never zero capacity or unlimited capacity. Unsaved zero/empty input is retained as a draft but cannot pass save validation. Multiple limits with the same basis, mode and compartment must be corrected rather than contradicted.

Catalog version 2 exposes which generic families can have explicitly confirmed independent compartments. Per-compartment limits use `resourceIndex` (one based); a whole-device 8 L capacity does not establish that each basket holds 8 L. An ordinary multicooker cannot gain another heating base by adding an inner pot or increasing a compartment count.

Shared preparation-space and equipment-storage constraints live on the kitchen. The primary kitchen has a stable identity and a partial unique primary-household index; additional non-primary kitchens can be represented later without implementing multi-home management now. Additive migrations 0077 and 0078 introduce these fields/indexes. Setup writes use the same expected kitchen revision and intent-bound durable receipts as equipment writes.

Personal cooking preferences are shared with AI only under recipe-preference consent, independently from equipment consent. They are no longer hidden inside the equipment context. General personal-profile saves cannot overwrite this separately revisioned preference owner. Direct Improve and queued/shared-context paths use these scoped context builders; all model-provided requirements remain generic and do not contain household assignments. Generated capacity-review flags prevent an unsupported fit claim when no comparable working limit was supplied.

## Coordinated meals and physical-use history

Open **Check a complete meal against My Kitchen**, or **Coordinate this meal with other recipes** from an owned cooking session. Add dinner components, review their exact steps/capabilities, resource quantities, hands-on work, dependencies and occupancy estimates, then compare parallel and sequential plans. A recipe without structured requirements opens an explicitly unverified placeholder for manual review. Nothing is inferred from recipe equipment text as ownership. Measured requirements, pressure-rated vessel requirements and cavity footprints can be reviewed without any AI provider.

A preview-only workspace creates no reservations. From a cooking episode, accept the complete meal plan and start only the phase actually beginning. Reopening retrieves the saved request/allocation and current claims. Serving changes, recipe revisions, availability and dated restrictions are rechecked. Separate meal entries are not treated as simultaneous unless explicitly coordinated in this workspace. The workspace currently starts from library recipes or an owned main-session snapshot; a full native coordinated-meal editor and arbitrary planner-entry selection remain open.

Migrations 0079 and 0080 preserve legacy active claims, introduce compatible shared-cavity claims and retain physical-use history with explicit release actor/time. A migrated bundle receives one stable use token and retains unknown legacy allocation as unknown. Passive vessels and unattached accessories cannot gain a heating base through arbitrary capability flags. Stovetop pressure tasks can declare a heat source plus `vesselCapability: pressure-vessel`; ordinary lidded cookware does not satisfy that requirement.

Session Markdown/JSON-LD/PDF exports resolve the same owned effective recipe. JSON-LD preserves generic method/equipment/rest/requirement metadata, and imports reject private assignment fields. Transport IDs and revision guards are hidden in normal web/native assistant value reviews; human target labels and actual proposed facts remain visible. A local synthetic backup/restore fixture preserves inventory IDs, receipts, cooking snapshots and occupied claims; this is not production/operator-volume recovery evidence.
