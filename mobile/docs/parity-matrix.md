# Bòrd mobile parity matrix

This matrix is the implementation contract between the web product and the Expo client. “Native” means the workflow stays in Expo and writes through the authenticated API. “Server” means the server remains authoritative and the device holds a scoped read cache.

| Product area                         | Expo implementation                                                                                                                | Authority / boundary                                                                                         |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Instance onboarding and account auth | Native instance validation, Better Auth email/passphrase, reset/recovery, SecureStore session                                      | Server session; passphrases are never persisted                                                              |
| Recipes                              | Native search, favorites, create, edit/revisions, cover upload, detail, ingredients, method, timing, cook mode                     | Server; recipe images use authenticated disk caching                                                         |
| Capture and import                   | Native text/URL capture, camera, Photos multi-select, PDF/image document picker, deterministic review draft, explicit confirmation | Server validates URLs/files; paid AI is never started automatically                                          |
| Collections and tags                 | Native list/create/delete collections, membership, and list/create/rename/delete tags                                              | Server                                                                                                       |
| Cook sessions                        | Native focused steps, persisted device progress, server cook session, explicit FEFO Pantry deduction review                        | Server; offline cooking remains readable but cannot claim completion                                         |
| Meal planning                        | Native day navigation, recipe selection, server additions, free-form meal display, assistant entry                                 | Server; advanced weekly regeneration/conflict resolution is exposed through review-first assistant proposals |
| Pantry                               | Native virtualized inventory, filters, batch detail, manual intake, edit, depletion, exact barcode lookup                          | Server; Pantry state is not inferred from shopping demand                                                    |
| Shopping lists                       | Native list creation, store profile display, shopper states, unavailable handling, checkout, exact barcode match/add               | Server                                                                                                       |
| Nutrition                            | Native profile/date selection, charts, household comparison, cache details, manual intake with immutable provenance                | Server; confirmed intake remains separate from planned portions                                              |
| Kitchen assistant                    | Native persisted threads/messages, paid-provider disclosure, server proposals, explicit confirm/discard                            | Server; no provider credential is stored in the app                                                          |
| Profiles and roles                   | Native profile inventory and PIN switching; account security is native                                                             | Profiles are convenience/attribution; the signed-in account remains access control                           |
| Backups                              | Native create/list/typed destructive restore with forced reauthentication                                                          | Server filesystem; portable archive export remains a server download                                         |
| Settings and integrations            | Device preferences, connection status, refresh, sign-out/change instance; server API/provider credentials stay outside the client  | SecureStore for session material; provider secrets remain server-only                                        |
| Offline                              | Account-and-instance-scoped SQLite read cache with honest empty/error/offline states                                               | Read-only; writes are never silently queued                                                                  |

## Target verification boundary

Static checks and platform bundles can run on Windows. Final visual acceptance still requires current iPhone and Android captures for safe areas, keyboard behavior, Dynamic Type, native-tab height, camera permissions, and the reference-image comparison described in `../design-qa.md`.

The web administration surface remains the canonical place for high-density maintenance workflows: recipe lifecycle/history export, collection ordering/covers, whole-week plan copy/status/ICS, Pantry catalog/location administration and correction history, store/aisle configuration, detailed Nutrition goal editing, background AI job administration, household role enrollment, API-key creation, diagnostics export, and portable backup download. The mobile client reads the results of those workflows and keeps their core everyday actions native; these administration surfaces should not be described as native parity until dedicated API-backed screens are added.
